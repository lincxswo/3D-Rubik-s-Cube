# 架构：文件一层层是怎么分的

这份文档回答三个问题：

1. 项目里的文件分成哪几层？
2. 每个文件具体干什么、依赖谁？
3. 为什么非要这么分？

---

## 1. 整体分层

```
                         ┌──────────────────────────┐
   页面骨架              │  index.html              │  只有两个容器：
  （浏览器直接加载）      │                          │  画布区 + 控制面板
                         └────────────┬─────────────┘
                                      │ 加载
                                      ▼
                         ┌──────────────────────────┐
   接线层                │  src/main.ts             │  唯一"认识所有人"的文件
  （第 4 层）            │  + src/style.css         │  管时序、管按钮状态
                         └───┬──────────┬───────────┘
                             │          │
              ┌──────────────┘          └──────────────┐
              ▼                                        ▼
  ┌──────────────────────────┐            ┌──────────────────────────┐
  │  src/ui/  （第 3 层）     │            │  src/render/ （第 2 层）  │
  │  界面控件                  │            │  3D 画面                   │
  │  controls.ts              │            │  cubeRenderer.ts          │
  │  · 生成 12 个转动按钮       │            │  · 摆 26 个小方块          │
  │  · 鼠标点击 / 悬停事件       │            │  · 上色、灯光、动画、描边    │
  └────────────┬─────────────┘            │  highlight.ts（纯规则）    │
               │                          └────────────┬─────────────┘
               │        （ui 只用 core 里的"记号类型"）    │
               └───────────────┬───────────────────────┘
                               ▼
                 ┌──────────────────────────────┐
                 │  src/core/  （第 1 层）        │
                 │  核心逻辑 —— 纯数据，不含 three  │
                 │  cubeState.ts  状态是什么       │
                 │  cubies.ts     方块在哪、朝向哪  │
                 │  moves.ts      12 种转动记号     │
                 │  turns.ts      转一层怎么算      │
                 │  scramble.ts   打乱 + 倒推计划   │
                 │  session.ts    模式、进度、容错  │
                 └──────────────────────────────┘
```

**依赖方向永远向下、单方向**，没有环：

```
index.html → main.ts → { ui, render } → core
                │                        ▲
                └──── render ─────────────┘
```

| 谁 | 允许引用 | 禁止引用 |
| --- | --- | --- |
| `core/` | 只有自己（core 内部互相引用） | 任何其它层、`three`、浏览器 API |
| `render/` | `core/`、`three`、自己的 `highlight.ts` | `ui/`、`main.ts` |
| `ui/` | `core/`（只用记号类型和解析函数）、浏览器 DOM | `render/`、`main.ts` |
| `main.ts` | 全部 | — |

> `core/` 里出现 `three` 会被 `src/core/separation.test.ts` 直接判定为失败。
> 这条测试就是"逻辑与画面分离"这条铁律的看门人。

## 2. 逐文件清单

### 第 1 层：核心逻辑层（`src/core/`）

| 文件 | 大概的作用 | 关键内容 |
| --- | --- | --- |
| `cubeState.ts` | **魔方状态本身**。回答"魔方现在长什么样" | 6 个面 × 9 格 = 54 格颜色；`createSolvedState` 造一个复原的魔方；`isSolved` 判断是否复原；`countByColor` 数每种颜色几格 |
| `cubies.ts` | **几何骨架**。回答"26 个小方块分别在哪、哪一面朝外" | 坐标（x 右 / y 上 / z 前，取值 -1、0、1）；`layerPositions` 某面那 9 个方块；`rotateClockwise` 把方向绕某个面转 90°；`cubieStickers` 把"状态"翻译成"每个方块露出来的颜色" |
| `moves.ts` | **转动记号**。回答"U' 是什么意思" | 12 种合法记号；`parseMove` 把 `R'` 拆成"右面 + 逆时针" |
| `turns.ts` | **转动的算法**。回答"转一步之后状态变成什么" | `applyMove` 走一步，`applyMoves` 连走多步。**不修改传进来的状态，而是返回新状态**（动画期间新旧两个状态要同时存在） |
| `scramble.ts` | **打乱与倒推**。回答"随机打乱 n 步"和"把一堆步骤反过来" | 步数限制 1~30（默认 20）；`createScramble` 生成随机步骤（天然不连续同面）；`createRestorePlan` 把一串步骤倒着排、每步反向 |
| `session.ts` | **会话状态机**。回答"现在是自由模式还是复原模式、走到第几步、该给什么提示" | 操作记录 `history`、复原计划 `plan`、进度 `cursor`、模式 `phase`、提示 `notice`；一键复原 / 下一步 / 上一步 / 退出复原模式 / 强行转动容错 / 重置 |

### 第 2 层：渲染层（`src/render/`）—— 唯一允许用 three 的层

| 文件 | 大概的作用 | 关键内容 |
| --- | --- | --- |
| `cubeRenderer.ts` | **把状态画成 3D，并演动画** | 场景、相机、灯光；26 个小方块（每块 6 个面各一份材质）；`render(state)` 上色；`animateMove` 播放 200ms 转层动画；`cancelMove` 立刻取消；`setHighlightedFace` 悬停高亮；`dispose` 释放显存 |
| `highlight.ts` | **高亮的纯规则**（不含 three，所以能直接测） | `stickerHighlight(方块位置, 指着的面)` 返回 `normal / glow / dim`；小方块边长、格位间距、描边边长三个尺寸常量 |

### 第 3 层：界面控件层（`src/ui/`）

| 文件 | 大概的作用 | 关键内容 |
| --- | --- | --- |
| `controls.ts` | **生成 12 个转动按钮，并上报用户意图** | 按钮从 `core/moves.ts` 的记号清单自动生成（按钮和"代码支持哪些转法"永远是同一份数据）；鼠标点击 → `onMove`；鼠标移入/移出 → `onHoverFace` |

### 第 4 层：接线层

| 文件 | 大概的作用 | 关键内容 |
| --- | --- | --- |
| `main.ts` | **唯一的总控**。把三层连起来，并管住时序 | 所有转动走同一个入口 `requestMove`（分"界面正常路径"和"绕过界面的强制路径"）；"忙"标志让动画期间不接受新指令；"代号"机制让被作废的动画不许再改数据 |
| `style.css` | 页面样式 | 上下布局（上：画布，下：控制面板）；按钮样式，含置灰状态 |

### 页面骨架与配置（不是逻辑代码）

| 文件 | 作用 |
| --- | --- |
| `index.html` | 页面骨架：`#viewport`（画布区）+ `#panel`（进度、提示、按钮）；只负责"把容器和按钮摆在页面上" |
| `package.json` | 项目清单：项目名、依赖清单、三条命令（`dev` / `test` / `build`） |
| `tsconfig.json` | TypeScript 的检查规则（严格模式相关配置在这里） |
| `.gitignore` | 哪些文件不进版本库（比如 `node_modules/`） |
| `package-lock.json` | 依赖的**精确版本锁**（自动生成，不要手改） |
| `AGENTS.md` | 给 AI 助手的协作规矩文件（**当前内容为空，见文末**） |
| `README.md` | 项目说明书（面向使用者） |
| `docs/` | 本套文档 |

### 测试文件（与被测文件放在一起）

| 文件 | 守着什么 |
| --- | --- |
| `src/smoke.test.ts` | 环境自检：测试框架能跑、three 能加载 |
| `src/core/cubeState.test.ts` | 初始状态必须是复原的；每种颜色刚好 9 格；标准配色正确 |
| `src/core/cubies.test.ts` | 26 个方块；8 角 / 12 棱 / 6 心；54 格贴纸不重不漏 |
| `src/core/turns.test.ts` | 顺时针方向的约定；同一面转 4 次回原位；`R` 再 `R'` 逐格复原；随机 1000 次颜色仍各 9 格 |
| `src/core/scramble.test.ts` | 步数 1~30 的限制；不连续同面；倒推计划走完必定复原 |
| `src/core/session.test.ts` | 单步前进/后退；复原模式；强行转动容错；重置；**400 次随机乱操作的压力测试** |
| `src/core/separation.test.ts` | **铁律**：`src/core/` 里不许出现 three，也不许引用渲染层 |
| `src/render/highlight.test.ts` | 12 个按钮 ↔ 6 个面的映射；高亮正好 9 个方块；切换不残留；描边尺寸约束 |

## 3. 三条典型数据流

### A. 点一个转动按钮

```
用户点按钮
   │
   ▼
src/ui/controls.ts       判定"这是哪个记号"，回调给 main
   │
   ▼
src/main.ts              算新状态：core/turns.ts 的 applyMove（拿到一个"新状态"，旧的纹丝不动）
   │                     若此刻在复原模式 → core/session.ts 顺带作废计划、给提示、退出复原模式
   ▼
src/render/cubeRenderer.ts   播 200ms 动画：把那一层的 9 个方块临时装进"转盘"转 90°
   │
   ▼
动画演完                  渲染层先把新状态的颜色刷上去，再把方块放回原位（看不出接缝）
   │
   ▼
src/main.ts              这时才把"新状态"提交为当前状态
```

关键点：**动画没演完之前，数据里还是旧状态**。所以动画中途被打断（用户绕过界面强行转动）时，只要不提交，数据就还是干净的。

### B. 打乱

```
用户输入 n、点【打乱】
   │
   ▼
core/scramble.ts         夹住 n（1~30）；生成 n 步随机步骤（天然不连续同面）
   │
   ▼
core/session.ts          beginScramble：把这次打乱步骤单独存一份，清掉上一次的复原计划
   │
   ▼
逐步                       每一步都走上面那条"点按钮"的流程，
                         但用 scrambleStep 把这一步记进"操作记录"（关键！）
```

### C. 复原（一键复原 + 下一步 / 上一步）

```
点【一键复原】
   │
   ▼
core/session.ts          enterRestoreMode：按"操作记录"算倒推计划
                         （记录倒着排 + 每步反向），进入复原模式
                         ★ 此时魔方一动不动，它只是把计划"装填"好
   │
   ├─ 点【下一步】→ stepForward：把记录里的最后一步"还掉"（反着转一次），并从记录里删掉它
   ├─ 点【上一步】→ stepBackward：把刚还掉的那步再转回去，并重新记回操作记录
   │
   ▼
记录被还空 = 魔方复原 = 操作记录自动清空（不需要额外的清理逻辑）
```

**为什么要记"操作记录"而不是只记打乱步骤？**
因为只记打乱的话，计划只能抵消打乱——前提是"打乱前魔方必须是复原的"。
一旦用户手动转过，这个前提就没了，那时候怎么重新打乱都回不到复原。
记下"真实做过的每一步"以后，倒推永远能走回复原，不管中间怎么折腾。

### D. 悬停高亮（完全不碰核心层）

```
鼠标移入按钮
   │
   ▼
src/ui/controls.ts       上报"现在指着哪个面"（移开就是 null）
   │
   ▼
src/render/cubeRenderer.ts  按 render/highlight.ts 的纯规则重算 26 个方块的观感：
                            那一层 9 个 → 发光 + 亮黄描边；其余 → 轻微压暗
```

整个过程中 `src/core/` **完全不知情**，所以高亮不可能改到状态数组，也不可能触发转动。

## 4. 为什么非要这么分？

| 好处 | 具体体现 |
| --- | --- |
| **逻辑可以脱离画面被验证** | 转动对不对、打乱规不规则、复原能不能走回去——全部是纯数据问题，测试里不需要开 3D 环境，跑一次 0.5 秒 |
| **画面可以独立改** | 换配色、加描边、调灯光，都不用担心影响魔方逻辑 |
| **同一份规则只写一遍** | "顺时针"这套数学，转数据用它、转画面也用它（`core/cubies.ts` 的 `rotateClockwise`），所以数据和画面不可能对不上 |
| **出错时容易定位** | 魔方转错了 → 一定是 `core/` 的问题；颜色/动画不对 → 一定是 `render/` 的问题；按钮没反应 → 一定是 `ui/` 或 `main.ts` |
| **规矩能被执行** | "core 不许用 three"不是口头约定，是一条会失败的测试 |

## 5. 目录里还有哪些"不是我们写的"

写文档时容易把这些和项目代码混在一起，这里明确分开：

| 东西 | 是什么 | 属于项目吗 |
| --- | --- | --- |
| `src/` | 我们自己写的全部代码 | ✅ 是 |
| `index.html`、`style.css` | 我们写的页面骨架和样式 | ✅ 是 |
| `package.json`、`tsconfig.json`、`.gitignore` | 我们写的配置 | ✅ 是 |
| `docs/`、`README.md`、`AGENTS.md` | 文档 | ✅ 是 |
| `node_modules/` | 从网上下载的第三方库（three、vite、vitest…） | ❌ 不是，不进版本库 |
| `package-lock.json` | 机器自动生成的版本锁 | ⚠️ 在项目里，但别手改 |
| `.git/` | 版本存档数据（由使用者自己维护） | ❌ 不是代码 |
| node / npm 安装在哪个目录、缓存目录在哪 | **机器环境**，项目之外 | ❌ 完全不属于项目，见 [development.md](./development.md) |

## 6. 当前的一个待办：`AGENTS.md` 是空的

`AGENTS.md` 原本写着协作规矩（每次只做一小步、每步必须写测试并跑 `npm test`、测试不过就停下来、不要动 git、用大白话解释）。
现在这个文件是 **0 字节**——内容疑似被搬进了 `README.md`。

影响：规矩只有 AI 助手在开工时读的那份文件里才有约束力。要不要把规矩整理回去，需要决定，
详见 [development.md 的说明](./development.md#agentsmd-的现状)。
