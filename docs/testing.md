# 测试

## 怎么跑

```bash
npm test
```

等价于 `vitest run`：**跑一遍、报结果、退出**（不会挂在监听模式）。
想看某一天的失败细节，可以跑 `npx vitest run --reporter=verbose`。

## 现状

- **8 个测试文件，76 条测试，全部通过，约 0.5 秒跑完。**
- 测试文件和被它测的代码**放在同一个目录**（`cubeState.ts` 和 `cubeState.test.ts` 挨着），
  改代码时一眼就能看到对应测试，不容易忘。

## 写新测试的规矩（照这个来）

1. **随机必须用固定种子。**
   项目里有一个小随机数生成器，同一个种子永远给同一串数。
   测试里**绝对不要用 `Math.random()`**——那样测试会时好时坏，出问题也没法复现。

2. **把"约定"直接写成断言，不要靠感觉。**
   比如"顺时针"到底往哪转，测试里是一张明明白白的对照表（`turns.test.ts`）。
   这类约定一旦搞反，程序照样能跑、颜色也不丢，只是方向全错，最难靠肉眼发现。

3. **优先断言"不变式"。**
   会话这一块最核心的不变式是：
   > 把操作记录里的步骤，从复原状态依次走一遍，必然等于当前状态。

   测试几乎每做一次操作就验一遍它（压力测试里连验 400 次）。

4. **先证明"操作真的生效了"，再断言结果。**
   例如"`R` 再 `R'` 应该复原"这条，先断言转完 `R` **确实乱了**，
   否则一个"什么都不做"的假实现也能蒙混过关。

5. **纯规则和画面分开测。**
   3D 画面需要浏览器的 WebGL，测试环境里没有。所以渲染层的做法是：
   把"哪 9 个方块该高亮"这类**纯规则**单独抽成一个不含 three 的文件（`render/highlight.ts`），
   测试直接验规则；真正"怎么画"的部分不测。

6. **重要功能配一条压力测试。**
   比如"随机乱操作 400 次：操作记录和状态永远对得上，且随时都能一键复原"。
   这种测试专门用来抓"逻辑判断出问题"这类隐蔽 bug。

## 测不了的部分（老实说）

- **3D 画面本身**：方块画得对不对、颜色好不好看、动画顺不顺、描边够不够明显——
  这些需要真实的浏览器和一双眼睛，自动化测试覆盖不到。
- 因此每次改动画面后，都需要人工在页面上看一眼（`npm run dev` 打开 `http://localhost:5173/`）。

## 测试失败怎么办

按项目规矩：**停下来报告，不要自己接着乱改。**
先把失败信息完整贴出来，确认是"代码错了"还是"测试本身写错了"，再动手。
